# 개발 전 결정·충돌 이력

## 1. 상태 정의

- **RESOLVED**: 1차 개발 결정 완료. 결정내용을 구현 기준으로 사용한다.
- **OPEN**: 추가 정책 또는 자료가 필요하다.
- 우선순위 P0/P1/P2는 최초 이슈의 영향도를 보존한다.

## 2. RESOLVED — OI-001~009 범위·용어·상태

### OI-001 — RESOLVED — 1차 MVP 범위

기존 쟁점: PDF는 작업완료까지, 상세설계 P1은 완료이력까지이며 AI/A·S/시설카드의 “필수”와 단계 우선순위가 충돌했다.

결정: MVP는 작업완료 후 기본 수리·서비스 이력 자동생성까지 포함한다. 후속 결정 OI-029와 OI-031에 따라 시설·제품 최소 기능과 최소 A/S도 포함한다. 명시 제외 기능은 별도 유지한다.

### OI-002 — RESOLVED — 거래 용어

기존 쟁점: `Deal`, `Transaction`, `/deals`, `/transactions` 혼용.

결정: 업무명 “거래”, 영문 도메인 `Transaction`, DB `transactions`, API `/api/v1/transactions`로 통일한다.

### OI-003 — RESOLVED — Provider 용어

기존 쟁점: Provider/Partner/공급자/기사 혼용과 조직-기사 관계.

결정: 영문은 `Provider`로 통일하고 MVP에는 조직-기사 구조를 구현하지 않는다.

### OI-004 — RESOLVED — API 규약

기존 쟁점: `/api/v1`, `/v1`, 버전 없는 경로와 JSON 표기 혼용.

결정: base path `/api/v1`, JSON camelCase를 사용한다.

### OI-005 — RESOLVED — DBMS/키

기존 쟁점: 관계형 DB, BIGINT/UUID 선택 미정.

결정: MS-SQL, 내부 PK BIGINT, 외부 UUID `publicId`를 사용한다.

### OI-006 — RESOLVED — 요청 상태

기존 쟁점: 작성중→검증중→모집준비→모집중→견적도착→결정대기의 영속 범위.

결정: `DRAFT/OPEN/ACCEPTED/EXPIRED/CANCELLED` 핵심 상태만 영속화한다. 견적도착·결정대기는 `hasQuotes`, `decisionPending` 등 파생값으로 처리한다.

### OI-007 — RESOLVED — 예약 단계

기존 쟁점: 상세 예약/방문예정과 PDF의 단순 거래→완료 간 차이.

결정: 복잡한 예약시스템은 MVP에서 제외한다. Transaction은 `CREATED→IN_PROGRESS→COMPLETION_SUBMITTED` 흐름을 사용한다.

### OI-008 — RESOLVED — 완료확정 주체

기존 쟁점: 완료 제출과 최종완료 주체, 고객 무응답.

결정: Provider가 작업완료를 제출하고 고객이 완료확정한다. 자동완료는 결정하지 않았으므로 OI-037 시간정책과 함께 운영 전 확정한다.

### OI-009 — RESOLVED — 분쟁 깊이

기존 쟁점: 상태 분기만 둘지 전체 운영까지 구현할지.

결정: MVP는 `DISPUTED` 상태와 증빙 구조까지만 포함한다. 담당배정·조정·해결·제재는 후속이다.

## 3. RESOLVED — OI-010~016 인증·카테고리·지역

### OI-010 — RESOLVED — 인증

기존 쟁점: 휴대폰/소셜/OIDC/본인인증/MFA 범위.

결정: MVP는 기본 계정 로그인을 구현한다. 소셜/OIDC/본인인증/MFA는 후속이다.

### OI-011 — RESOLVED — Provider 승인

기존 쟁점: 사업자·자격·보험·계좌의 상세 검증 기준.

결정: Provider는 관리자 승인상태를 가진다. 상세 증빙 검증은 후속이다. Excel 관리대장의 82개 자격·안전 정책은 기준값으로 저장하되 MVP 승인 적격식에 자동 강제하지 않는다.

### OI-012 — RESOLVED — 카테고리 초기 데이터

기존 쟁점: 6/82/677/837 실제 목록 부재와 임시 카테고리 생성 위험.

결정: `수달_라이프_전체_서비스_카테고리_및_수수료_관리대장_v1.2.xlsx`를 Source of Truth로 사용한다. 임시 전체 카테고리를 만들지 않는다. 관리대장 실측은 677개 하위 서비스와 837개 동적필드이며, v1.2에서 FEE-I1을 최종 시공업체 선택 시 선택 견적금액 구간에 따라 차감하도록 확정했다.

### OI-013 — RESOLVED — 카테고리 이력

기존 쟁점: 카테고리 자체 버전 복제 대 단순 활성값.

결정: 카테고리 마스터+변경감사+Transaction 스냅샷 방식으로 한다. 관리대장 정책버전과 적용일을 보존한다.

### OI-014 — RESOLVED — 동적 요청필드

기존 쟁점: 고정 필드로 시작할지 관리대장 동적필드를 포함할지.

결정: MVP에 포함한다. 관리대장 837개 정의의 필드키·유형·필수·선택값/단위·Provider 공개·채택 전 마스킹·검증규칙을 사용한다.

### OI-015 — RESOLVED — 행정구역 설계

기존 쟁점: 행정구역 단위와 기준.

결정: 공식 시·군·구 코드 기반으로 설계한다. 실제 코드 데이터 파일·갱신 Source·폐지코드 매핑 자료는 개발 착수 자료로 별도 필요하다.

### OI-016 — RESOLVED — 출장지역 모델

기존 쟁점: ProviderCoverageArea/ProviderServiceArea 등 명칭 혼용.

결정: 도메인 `ProviderServiceArea`, DB `provider_service_areas`, API `/providers/me/service-areas`로 통일한다.

## 4. RESOLVED — OI-017~025 매칭·견적·채택

### OI-017 — RESOLVED — 후보와 배포

기존 쟁점: 후보 계산과 공급자 노출을 한 테이블로 둘지.

결정: `DispatchCandidate`와 `RequestDispatch`를 분리한다.

### OI-018 — RESOLVED — 알림톡

기존 쟁점: 문서/관리대장은 일치 Provider에게 알림톡을 요구하지만 MVP 실연동 여부가 미정이었다.

결정: 실제 카카오 알림톡 연동은 MVP에서 제외하고 알림 이벤트/로그 구조만 구현한다. 관리대장 R-002 및 카테고리 알림정책은 후속 연동 기준값으로 보존한다.

### OI-019 — RESOLVED — 기본 매칭조건

기존 쟁점: 가용시간·수행한도·자격만료까지 포함할지.

결정: 카테고리+시군구+Provider 승인+활성상태를 기본 조건으로 한다.

### OI-020 — RESOLVED — 견적 마감/최대 견적수

기존 쟁점: 기본 마감과 최대 견적수 미정.

결정: 전역 기본 마감은 3일(72시간)이며 설정값으로 관리한다. Excel 관리대장에 카테고리별 `견적 유효시간`이 있으면 그 값이 우선한다. 현재 값은 627개 서비스 72시간, 50개 서비스 2시간이다. 최대 견적수는 관리대장 값(현재 전 카테고리 5)을 사용한다.

### OI-021 — RESOLVED — 견적 revision

기존 쟁점: 수정 시점과 기존차수 보존.

결정: 채택 전까지 수정 가능하며 모든 revision을 보존한다. 채택은 최신 유효 revision을 다시 검증한다.

### OI-022 — RESOLVED — 견적 금액

기존 쟁점: 단일 총액 대 subtotal/tax/item 구조.

결정: 총액, VAT 포함여부, 견적 항목내역을 지원한다. 실제 결제/세금계산은 MVP에서 하지 않는다.

### OI-023 — RESOLVED — 신뢰점수

기존 쟁점: 문서/관리대장은 `CREDIT_DESC` 기본정렬을 요구하지만 점수 산식이 미정이었다.

결정: 신뢰점수 계산은 MVP에서 제외하고 “신규·평가중”만 지원한다. 관리대장의 표시/정렬 정책은 후속 기준값으로 보존하며 임시 점수를 생성하지 않는다.

### OI-024 — RESOLVED — 수수료/충전금

기존 쟁점: 채택과 수수료차감 원자처리 대 P2 분리.

결정: 견적수수료 및 충전금 차감은 MVP에서 제외한다. 관리대장 FEE-Q1~Q7 등 수수료 값은 보존하되 견적/채택의 선행조건으로 사용하지 않는다.

### OI-025 — RESOLVED — 결제

기존 쟁점: 직접결제 확인 테이블을 MVP에 둘지.

결정: 결제기능은 제외하고 Provider 작업완료 시 실제 작업금액만 기록한다.

## 5. RESOLVED — OI-026~033 완료·이력·A/S

### OI-026 — RESOLVED — 완료 공통 증빙

기존 쟁점: 공통 완료증빙과 카테고리별 차등 기준.

결정: 실제 작업금액과 작업내용은 MVP 공통 완료정보다. 작업 전·후 사진은 공통 기본 권장 원칙이며, 필수 사진 개수와 역할은 OI-039에 따라 관리대장의 카테고리별 완료증빙 정책을 우선한다.

### OI-027 — RESOLVED — 파일저장소

기존 쟁점: 저장소·개발환경 방식.

결정: 파일저장소를 추상화하고 개발환경에서 로컬 저장을 허용한다. 파일 포맷·보존기간·악성검사는 OI-034/038 및 추가 자료에서 구체화한다.

### OI-028 — RESOLVED — 이력 저장

기존 쟁점: 동적 조회 대 영속 이력 사건.

결정: 고객 완료확정 시 `ServiceHistoryEntry`를 영속 생성하고 멱등성을 보장한다.

### OI-029 — RESOLVED — 시설·제품 카드

기존 쟁점: P1 기본이력 대 P4 시설카드.

결정: MVP에 최소 등록·조회·Transaction 연결을 포함한다.

### OI-030 — RESOLVED — 이력 접근

기존 쟁점: Provider의 고객 시설이력 열람 범위.

결정: 소유 고객과 해당 Transaction Provider로 제한한다. Provider는 해당 거래에 연결된 범위만 조회한다.

### OI-031 — RESOLVED — 최소 A/S

기존 쟁점: 보증조건만 둘지 전체 운영까지 할지.

결정: `RECEIVED→IN_PROGRESS→COMPLETED` 상태와 원 거래/이력 연결을 MVP에 포함한다. 고급 SLA·분쟁·보상 운영은 후속이다.

### OI-032 — RESOLVED — 보증기간

기존 쟁점: 시작일과 warrantyDays/warrantyTo 혼용.

결정: 고객 완료확정일을 시작일로 하고 `warrantyDays`로 계산한다. 관리대장 기본 A/S일(현재 0/3/30일)을 카테고리 기본값으로 사용하고 Transaction 스냅샷을 우선한다.

### OI-033 — RESOLVED — 재방문/새 거래

기존 쟁점: A/S 재방문과 유상 추가작업 구분.

결정: 보증 범위 내 재방문은 A/S 사건, 별도 유상 추가작업은 새 요청/Transaction으로 처리한다.

## 6. RESOLVED — OI-039 완료증빙

### OI-039 — RESOLVED — 완료사진/증빙 정책 우선순위 (P0)

기존 쟁점: OI-026의 공통 전·후 사진 원칙과 관리대장의 카테고리별 필수사진 0/2/5 및 완료증빙 값 사이의 적용 우선순위와 제출 차단규칙이 불명확했다.

결정:

1. 완료 증빙 사진의 필수 개수는 서비스 카테고리별 정책값을 최우선으로 적용한다.
2. 수달 라이프 서비스 카테고리 및 수수료 관리대장의 완료증빙/필수사진 정책을 Source of Truth로 사용한다.
3. 공통 설계서의 “작업 전 사진 + 작업 후 사진” 규칙은 기본 권장 원칙이며 모든 카테고리에 일률적으로 2장을 강제하지 않는다.
4. `requiredPhotoCount=0`이면 사진 없이 완료 제출할 수 있다.
5. `requiredPhotoCount=2`이면 최소 2장의 완료사진을 요구한다.
6. `requiredPhotoCount=5`이면 최소 5장의 완료사진을 요구한다.
7. 향후 다른 숫자도 사용할 수 있도록 숫자를 프로그램에 하드코딩하지 않는다.
8. 완료 제출 시 서버가 Transaction의 카테고리와 적용된 완료증빙 정책을 조회하여 필수사진 개수를 검증한다.
9. Transaction 생성 또는 작업 수행 시 적용된 카테고리 정책버전 또는 스냅샷을 보존하여 이후 관리대장 정책변경이 기존 거래의 완료조건을 소급 변경하지 않게 한다.
10. 카테고리 정책에 사진별 역할이 정의된 경우 `BEFORE`, `AFTER`, `DETAIL`, `SERIAL`, `DAMAGE` 등의 역할별 필수 여부도 검증할 수 있도록 확장 가능하게 설계한다.

## 7. OPEN — 운영환경 전 결정

### OI-034 — OPEN — 개인정보 보유기간 (P2)

필요 결정: 회원·요청·동적응답·상세주소·사진·견적·Transaction·A/S·감사별 보유/파기/익명화 기간과 법적 근거.

### OI-035 — OPEN — 관리자 권한·MFA·재인증 (P2)

필요 결정: 관리자 역할별 권한, 운영환경 MFA, 민감조회 재인증, 마스킹 해제 승인/사유, 대량내보내기 제한.

### OI-036 — OPEN — 성능·가용성 (P2)

필요 결정: 동시 사용자, 545개 MVP 카테고리와 Provider 규모, 후보 계산 응답시간, 가용성, RPO/RTO, 백업/복구 목표.

### OI-037 — OPEN — 시간·영업일 정책 (P2)

필요 결정: 견적마감·고객 완료무응답·보증종료일의 경계 포함 여부, 휴일/영업일, Asia/Seoul 변환, 배치 실행시각.

### OI-038 — OPEN — 감사로그 보존·민감정보 (P2)

필요 결정: 감사 대상 필드, before/after의 암호화·마스킹, 보존기간, 열람권한, 다운로드 통제.
