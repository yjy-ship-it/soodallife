# 1차 MVP 범위

## 1. 범위 기준

MVP는 PDF의 단일 거래 폐쇄루프에 기본 수리·서비스 이력 자동생성, 시설·제품 최소 기능, 최소 A/S를 더한 범위다. 실제 카테고리와 동적필드는 Excel 관리대장 v1.1을 사용한다.

## 2. 포함 범위

| 영역 | 포함 기능 | 완료 기준 |
|---|---|---|
| 인증/역할 | 기본 계정 로그인, 고객/Provider/관리자 역할 | 역할+객체관계 권한 분리 |
| Provider | 최소 프로필, 관리자 승인·활성 상태 | 승인·활성 Provider만 매칭/견적 |
| 카테고리 | 관리대장 마스터, `ACTIVE/PAUSED/REVIEW`, 거래유형 | MVP에는 `ACTIVE+ONE_TIME`만 노출 |
| 동적필드 | 필드키·유형·필수·선택값·공개·마스킹·검증 | 카테고리별 스키마 조회와 서버 검증 |
| 행정구역 | 공식 시·군·구 코드 | 요청/출장지역 동일 코드 사용 |
| 공급범위 | 공급 카테고리와 `ProviderServiceArea` | 카테고리별 복수 지역·중복 방지 |
| 요청 | 임시저장, 동적응답, 공개, 마감 | 필수값 검증 후 `OPEN` |
| 후보 | 카테고리+시군구+승인+활성 계산 | 불일치 Provider 제외, 근거 저장 |
| 배포 | 후보 중 실제 노출 기록, 요청함 | 후보와 분리, 중복 배포 없음 |
| 알림 | 이벤트·로그 | 외부 알림톡 호출 없음 |
| 견적 | 총액, VAT, 항목, 범위, 일정, 보증 | 채택 전 수정 가능, 이력 보존 |
| 채택 | 유효 견적 1건 채택 | 동시 시도에도 한 건만 성공 |
| 거래 | `Transaction`과 채택 스냅샷 | 채택과 거래생성 원자 처리 |
| 완료 | 작업내용·실제금액·카테고리 정책별 증빙, 고객 확인 | 정책 스냅샷 검증 후 정상/보완/분쟁 분기 |
| 이력 | 완료확정 시 `ServiceHistoryEntry` | 동일 거래/완료차수에 한 건 |
| 시설·제품 | 최소 등록·조회·거래연결 | 소유/거래관계 권한 검사 |
| A/S | 접수→진행→완료, 원 거래/이력 연결 | warrantyDays 기반 보증 표시 |
| 파일 | 저장소 추상화, 개발환경 로컬 저장 | 원본/메타데이터/접근권한 분리 |

## 3. 관리대장 적용 규칙

- 677개 하위 서비스 중 `ONE_TIME` 545개만 MVP 공개 대상이다.
- `SUBSCRIPTION` 45개와 `PROJECT` 87개는 기준정보를 보존하되 노출하지 않는다.
- 동적필드 837개를 임의 축약하지 않는다. 적용 서비스/중분류에 따라 필드 스키마를 조합한다.
- 카테고리별 견적 유효시간은 관리대장 값(현재 2시간 50개, 72시간 627개)을 우선한다.
- 관리대장 값이 없는 경우에만 전역 기본 72시간을 사용하며 설정값으로 관리한다.
- 최대 견적수는 관리대장 값(현재 전 카테고리 5)을 정책으로 읽는다.
- 기본 A/S일은 관리대장 값(현재 0/3/30일)을 `warrantyDays` 기본값으로 사용한다.
- 수수료·자격·신뢰점수 정책값은 보존하되 MVP 실행 로직에서는 제외된 범위를 강제하지 않는다.
- 완료증빙과 필수사진 수는 관리대장의 카테고리 정책을 최우선으로 적용한다. 공통 설계서의 작업 전·후 사진은 기본 권장 원칙이지 모든 카테고리의 일률적 필수조건이 아니다.
- `requiredPhotoCount=0`은 사진 없이 제출 가능하고, 2와 5는 각각 최소 2장과 5장을 요구한다. 향후 다른 숫자도 정책값으로 처리하며 프로그램에 허용값을 하드코딩하지 않는다.
- 완료 제출 서버는 Transaction의 카테고리와 적용 완료증빙 정책 스냅샷을 조회하여 사진 개수와, 정의된 경우 `BEFORE/AFTER/DETAIL/SERIAL/DAMAGE` 등 역할별 필수조건을 검증한다.
- 적용 정책버전 또는 스냅샷을 Transaction 생성 또는 작업 수행 시 보존하여 이후 관리대장 변경을 기존 거래에 소급 적용하지 않는다.

## 4. 핵심 E2E 인수 시나리오

1. 관리대장 카테고리와 동적필드가 조회된다.
2. 승인 Provider A가 카테고리/강남구를, B가 다른 지역을 등록한다.
3. 고객이 필수 동적필드를 입력하여 강남구 요청을 공개한다.
4. A만 후보가 되고 배포 후 A 요청함에만 노출된다.
5. 둘 이상의 적격 Provider가 견적을 제출·수정하고 이력이 보존된다.
6. 고객이 한 견적을 채택하며 동시 채택은 한 건만 성공한다.
7. `Transaction`은 하나만 생성되고 채택 전 민감정보는 노출되지 않는다.
8. Provider가 거래에 보존된 카테고리 정책의 사진 개수·역할 조건을 충족하는 완료자료를 제출하고 고객이 정상완료를 확정한다.
9. `ServiceHistoryEntry`가 한 번 생성되고 고객/Provider 이력값이 일치한다.
10. 고객이 시설·제품을 등록하고 거래를 연결한다.
11. 보증 범위 내 A/S를 접수→진행→완료하고 원 거래 이력에서 조회한다.

## 5. 명시적 제외

- AI 전 기능
- 정기구독/수달 케어
- GPS/QR 방문인증
- PG/정기결제/월말정산/지급
- 인테리어 프로젝트
- 모바일 앱
- 실제 알림톡 전송
- 신뢰점수 계산 및 점수정렬
- 견적수수료·충전금 차감
- 결제/직접결제 확인
- 고급 전문가 증빙검증
- 복잡한 예약시스템
- 분쟁 전체 운영워크플로

## 6. 금지되는 선행 결합

- AI 응답 없이는 요청을 공개할 수 없는 구조
- 충전금·수수료·결제 없이는 견적/채택할 수 없는 구조
- GPS/QR 없이는 완료할 수 없는 구조
- 시설·제품 연결 없이는 기본 완료 이력을 만들 수 없는 구조
- A/S 사건이 원 `Transaction` 없이 존재하는 구조
