# 핵심 업무 흐름

## 1. 전체 흐름

`카테고리·동적필드 → Provider 공급범위 → 고객 요청 → 후보 → 배포 → 견적/수정 → 단일 채택 → Transaction → 완료확정 → ServiceHistoryEntry → 시설·제품/A·S`

## 2. BF-01 카테고리·동적필드 관리

- Excel 관리대장의 카테고리코드, 대·중·하위 분류, 거래유형, 요청방식, 사용상태, 정책버전을 저장한다.
- `CategoryFieldDefinition`에 필드ID, 필드키, 적용 서비스, 유형, 필수여부, 선택값/단위, Provider 공개, 채택 전 마스킹, 검증규칙을 저장한다.
- 상태는 관리대장 코드 `ACTIVE/PAUSED/REVIEW`를 사용한다.
- MVP 사용자 선택에는 `ACTIVE+ONE_TIME`만 노출한다.
- 카테고리는 마스터+변경감사로 관리하고 Transaction에 당시 스냅샷을 보존한다.

## 3. BF-02 Provider 카테고리·출장지역

선행조건: Provider가 `APPROVED+ACTIVE`.

- Provider가 공급 카테고리를 선택한다.
- `ProviderServiceArea`에 카테고리별 공식 시·군·구를 복수 등록한다.
- Provider+카테고리+지역 활성 중복을 금지한다.
- 비활성 지역은 신규 후보 계산에서 제외하되 과거 기록은 보존한다.

## 4. BF-03 고객 요청

- 고객은 `ACTIVE+ONE_TIME` 하위 카테고리를 선택한다.
- 시스템은 해당 카테고리에 적용되는 동적필드 스키마를 반환한다.
- 고객은 필수 필드에 응답하고 공개한다.
- 서비스 주소는 공개 시·군·구 코드와 암호화 상세주소로 분리한다.
- 카테고리별 견적 유효시간이 있으면 우선 적용한다. 현재 관리대장 값은 2시간 또는 72시간이다.
- 값이 없을 때만 전역 기본 72시간을 사용하며 하드코딩하지 않는다.
- 최대 견적수는 관리대장 정책값(현재 5)을 적용한다.

## 5. BF-04 후보 계산

필수 조건:

1. 요청이 `OPEN`이고 마감 전
2. 요청 카테고리가 `ACTIVE+ONE_TIME`
3. Provider가 `APPROVED+ACTIVE`
4. Provider가 해당 카테고리를 공급
5. 활성 `ProviderServiceArea`의 시·군·구가 요청과 일치

산출: `DispatchCandidate`와 당시 적격 근거. 가용시간, 거리, GPS, 신뢰점수, AI 적합도는 MVP 조건이 아니다.

## 6. BF-05 배포·요청 표시

- 후보 중 실제 노출 대상을 `RequestDispatch`로 별도 생성한다.
- Provider 요청함은 본인의 유효 배포만 반환한다.
- 요청번호, 카테고리, 시·군·구, 요약, 희망일, 마감을 표시한다.
- 고객 성명, 전화, 상세주소는 반환하지 않는다.
- 실제 카카오 알림톡은 호출하지 않고 알림 이벤트와 로그만 기록한다.

## 7. BF-06 견적 제출·수정

필수 입력:

- 총액, VAT 포함 여부
- 견적 항목내역
- 작업범위, 포함/제외·추가비용 조건
- 방문 가능일, 예상시간
- `warrantyDays`와 A/S 조건

검증:

- 요청이 공개/마감 전이고 Provider에게 유효 배포가 있음
- Provider가 제출 시점에도 승인·활성·지역 적격
- 요청+Provider 활성 견적은 하나
- 채택 전까지만 수정 가능하며 각 revision을 보존

## 8. BF-07 비교·단일 채택

- 고객은 본인 요청의 유효 견적만 본다.
- 신뢰점수 계산은 하지 않고 Provider를 “신규·평가중”으로 표시한다.
- 고객이 한 건을 채택하면 견적 유효성, Provider 상태, 기존 Transaction을 재검증한다.
- 채택 견적 확정, 요청 `ACCEPTED`, `Transaction` 생성, 나머지 견적 `NOT_SELECTED`를 한 트랜잭션으로 처리한다.
- 수수료·충전금·결제는 실행하지 않는다.

## 9. BF-08 Transaction·작업완료

- Transaction은 요청, 채택 견적, 고객, Provider, 채택시각, 당시 조건 스냅샷을 가진다.
- Transaction 생성 또는 늦어도 작업 수행 시 관리대장의 적용 완료증빙 정책버전/스냅샷을 고정한다.
- 복잡한 예약시스템은 없다.
- Provider는 작업시작 후 작업내용, 실제 작업금액, 카테고리 정책에 맞는 증빙을 제출한다.
- 서버는 현재 관리대장 값이 아니라 Transaction에 고정된 정책에서 `requiredPhotoCount`를 읽어 최소 사진 수를 검증한다. 값 0은 사진 없이 제출 가능하고 2와 5는 각각 최소 2장과 5장이며, 다른 숫자도 같은 방식으로 처리한다.
- 정책에 사진 역할이 정의되면 `BEFORE/AFTER/DETAIL/SERIAL/DAMAGE` 등의 역할별 필수조건도 함께 검증한다. 공통 전·후 사진 규칙은 정책에 역할이 없을 때의 권장 원칙이다.
- 고객은 `COMPLETED`, `REVISION_REQUESTED`, `DISPUTED` 중 하나로 확인한다.
- 분쟁은 상태와 증빙만 보존하고 전체 운영은 후속이다.

## 10. BF-09 완료 이력

- 고객 `COMPLETED` 확정이 트리거다.
- 동일 Transaction+확정 완료차수에 `ServiceHistoryEntry(COMPLETION)` 한 건을 영속 생성한다.
- 원 요청, 채택 견적, Transaction, 완료증빙, 고객 확인을 연결한다.
- 고객/Provider는 같은 사건을 각 권한에 맞게 조회한다.

## 11. BF-10 시설·제품

- 고객은 최소정보로 `ServiceAsset`을 등록·조회한다.
- 본인 Transaction을 `TransactionAssetLink`로 연결한다.
- 해당 거래 Provider는 거래 범위의 자산/이력만 본다.
- 정정은 원 링크를 덮어쓰지 않고 감사 이력을 남긴다.

## 12. BF-11 최소 A/S

- 완료된 원 Transaction을 기준으로 고객이 A/S를 접수한다.
- 보증 시작일은 고객 완료확정일이고 `warrantyDays`로 종료일을 계산한다.
- 상태는 `RECEIVED → IN_PROGRESS → COMPLETED`다.
- 접수/진행/완료 사건을 서비스 이력에 추가한다.
- 보증 범위 내 재방문은 A/S 사건으로 처리한다.
- 별도 유상 추가작업은 새로운 요청과 Transaction으로 처리한다.

## 13. 예외

| 예외 | 처리 |
|---|---|
| 후보 0명 | 요청 유지, 고객/관리자에 표시; 자동 범위확대 없음 |
| 알림 로그 실패 | 요청/배포는 유지하고 실패·재시도 기록 |
| 견적 0건 마감 | 요청 `EXPIRED` |
| 철회/만료 견적 채택 | 409 업무충돌 |
| 동시 채택 | 한 건만 성공 |
| 완료 보완 | 기존 완료차수 보존, 새 revision 제출 |
| 분쟁 | Transaction `DISPUTED`, 증빙 보존 |
| 이력 재처리 | 멱등키로 중복 없음 |
| 카테고리 비활성 | 신규 선택 제외, 과거 스냅샷 유지 |

## 14. 완료증빙 정책 우선순위

- Excel 관리대장의 카테고리별 완료증빙/필수사진 정책이 Source of Truth다.
- 공통 설계서의 작업 전·후 사진은 기본 권장 원칙이며 카테고리 정책을 덮어쓰지 않는다.
- 완료 제출 검증은 Transaction에 보존된 적용 정책 스냅샷을 사용한다. 이후 관리대장 정책변경은 기존 Transaction의 제출조건을 바꾸지 않는다.
- 사진 개수와 사진 역할은 데이터로 해석하며 0/2/5 또는 역할 코드를 프로그램 분기로 하드코딩하지 않는다.
