# 수달 라이프 개발 착수 전 통합 개요

## 1. 공식 기준

현재 개발의 Source of Truth는 다음 네 문서다.

- `수달_라이프_주요_내용_통합정리서_v1.2.docx`
- `수달_라이프_전체_시스템_개발_통합상세설계서_v1.2.docx`
- `수달_라이프 _1차_MVP.pdf`
- `수달_라이프_전체_서비스_카테고리_및_수수료_관리대장_v1.2.xlsx`

Excel 관리대장은 카테고리, 동적 요청필드, 수수료, 자격·안전·운영정책 및 완료증빙/필수사진 정책의 실제 기준값이다. 문서와 관리대장이 충돌하면 임의 보정하지 않고 `OPEN_ISSUES.md`에 기록한다. OI-001~033과 OI-039의 RESOLVED 결정은 1차 개발 범위를 구체화하는 승인 기준이다.

## 2. 관리대장 기준 현황

- 기준일: 2026-08-02, 정책버전 v1.1
- 대분류 6개, 중분류 82개, 하위 서비스 677개
- 동적 요청필드 837개: 필수 550개, 선택 287개
- 자격·안전 정책 82개
- 거래유형: `ONE_TIME` 545개, `SUBSCRIPTION` 45개, `PROJECT` 87개
- 현재 하위 서비스 677개는 모두 “사용” 상태로 기재됨
- MVP 공개 대상은 `ONE_TIME`이면서 사용상태가 `ACTIVE`인 하위 서비스다.
- 구독·인테리어 데이터는 삭제하지 않고 MVP 선택목록과 업무진입에서 제외한다.

## 3. 확정 기술·용어 기준

- 업무명: 거래
- 영문 도메인: `Transaction`
- DB 테이블: `transactions`
- API resource: `/api/v1/transactions`
- 전문가 영문 용어: `Provider`
- 조직-기사 구조: MVP 제외
- API base path: `/api/v1`
- JSON: camelCase
- DBMS: MS-SQL
- 내부 PK: BIGINT
- 외부 공개 식별자: UUID `publicId`

## 4. 1차 MVP 폐쇄루프

1. 관리자가 관리대장 기반 카테고리·동적필드·정책을 등록/조회한다.
2. 승인·활성 Provider가 공급 카테고리와 카테고리별 `ProviderServiceArea`를 등록한다.
3. 고객이 카테고리를 선택하고 해당 동적필드에 응답하여 요청을 공개한다.
4. 시스템이 카테고리+시·군·구+Provider 승인+활성 조건으로 후보를 계산한다.
5. 후보와 실제 배포를 분리 기록하고 Provider 요청함에 노출한다.
6. Provider가 총액, VAT 포함 여부, 항목내역, 범위, 일정, 보증조건을 포함한 견적을 제출한다.
7. 고객이 견적을 비교하고 정확히 한 건을 채택한다.
8. 채택과 `Transaction` 생성을 원자적으로 수행한다.
9. Provider가 작업을 수행하고 작업내용, 실제 작업금액, 필수 증빙을 제출한다.
10. 고객이 정상완료, 보완요청 또는 분쟁을 선택한다.
11. 정상완료 확정 시 `ServiceHistoryEntry`를 멱등하게 영속 생성한다.
12. 고객이 시설·제품을 최소 등록·조회하고 거래와 연결한다.
13. 보증 범위 내 A/S를 접수→진행→완료 상태와 이력 사건으로 원 거래에 연결한다.

## 5. 핵심 불변조건

- 요청당 활성 `Transaction`은 최대 1개다.
- 요청+Provider당 활성 견적은 최대 1개이며 수정이력은 보존한다.
- 후보 계산과 배포 기록은 별도 엔터티다.
- 채택·거래 생성·완료확정·이력 생성은 재시도에도 중복되지 않는다.
- 채택 전 상세주소·연락처는 Provider에게 공개하지 않는다.
- 매칭은 GPS가 아닌 공식 시·군·구 코드의 정확 일치를 사용한다.
- 카테고리는 마스터+변경감사+거래 스냅샷 방식이다.
- 완료사진 필수 개수와 선택적 사진 역할은 Transaction에 보존된 카테고리 완료증빙 정책을 기준으로 서버가 검증하며 숫자를 하드코딩하지 않는다.
- 완료 이력은 별도 거래가 아니라 기존 요청·견적·Transaction·완료증빙의 연결 계층이다.
- 전문가가 완료자료를 제출하고 고객이 완료를 확정한다.
- 분쟁은 MVP에서 상태와 증빙까지만 보존한다.

## 6. MVP 포함

- 기본 계정 로그인과 고객/Provider/관리자 역할
- Provider 관리자 승인/활성 상태
- 관리대장 기반 카테고리·동적 요청필드
- 공식 시·군·구 기준 및 `ProviderServiceArea`
- 요청 작성·공개, 후보 계산, 배포, Provider 요청함
- 견적 제출·수정이력, 비교, 단일 채택
- `Transaction`, 작업진행, 완료자료, 고객 완료확정
- `ServiceHistoryEntry` 영속 생성과 양측 이력조회
- 시설·제품 최소 등록·조회·거래연결
- 최소 A/S 접수→진행→완료와 이력연결
- 파일저장 추상화와 개발환경 로컬 저장
- 권한, 개인정보 마스킹, 감사, 멱등성

## 7. MVP 제외

- AI 요청작성·견적·추천·이상탐지
- 정기구독, GPS/QR, PG 결제, 월말 정산
- 인테리어, 모바일 앱
- 실제 카카오 알림톡 전송(이벤트/로그만 포함)
- 신뢰점수 계산·등급 산정·점수 기반 정렬
- 견적수수료·충전금 차감, 결제 확인
- 소셜/OIDC/본인인증/관리자 MFA
- 복잡한 예약·캘린더·상호 예약승인
- 분쟁 담당배정·조정·해결 전체 워크플로

## 8. 남은 개발 착수 게이트

OI-034~038이 OPEN이다. 개인정보 보존, 관리자 보안, SLO, 시간정책, 감사로그 정책은 관련 운영환경 구축 전에 확정해야 한다.
