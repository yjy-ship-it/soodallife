# 사용자 역할과 권한 경계

## 1. 공통 원칙

- 한 계정은 여러 역할을 가질 수 있으나 화면·API 권한은 분리한다.
- 영문 전문가 용어는 `Provider`다.
- MVP에서는 조직과 소속 기사 구조를 구현하지 않는다.
- 역할 권한과 객체 소유/거래관계를 함께 검사한다.
- Provider 역할 보유와 관리자 승인은 별개다.

## 2. 고객

### MVP 권한과 책임

- `ACTIVE+ONE_TIME` 카테고리 및 동적 요청필드 조회
- 요청 임시저장·공개·상태조회
- 본인 요청의 유효 견적 비교 및 한 건 채택
- 본인 `Transaction` 진행·완료자료 조회
- Provider 완료제출에 대한 정상완료·보완·분쟁 선택
- 본인 수리·서비스 이력 조회
- 본인 시설·제품 최소 등록·조회·거래연결
- 본인 거래의 A/S 접수·상태·이력 조회

### 제한

- 다른 고객의 요청·거래·시설·이력에 접근하지 못한다.
- 채택완료 요청에서 추가 견적을 채택하지 못한다.
- 완료확정된 원 거래·증빙을 직접 덮어쓰지 않는다.
- A/S는 완료된 본인 거래에만 접수한다.

## 3. Provider

### MVP 진입 조건

- Provider 역할과 최소 프로필
- 관리자 승인 상태 `APPROVED`
- 활동 상태 `ACTIVE`

### MVP 권한과 책임

- 공급 카테고리 및 카테고리별 `ProviderServiceArea` 관리
- 후보 산출 후 본인에게 배포된 요청만 조회
- 채택 전 마스킹 요청을 기준으로 견적 제출·수정·철회
- 본인 채택 `Transaction` 조회 및 작업 시작
- 작업내용·실제금액과 Transaction에 적용된 카테고리 정책별 완료증빙 제출/보완
- 본인 작업·수리 이력 조회
- 해당 거래와 연결된 시설·제품을 거래 범위에서만 조회
- 해당 거래 A/S 진행·완료 및 증빙 등록

### 제한

- 미승인/비활성 상태에서는 매칭·견적을 수행하지 못한다.
- 타 Provider의 견적·거래·작업이력을 조회하지 못한다.
- 채택 전 상세주소·연락처를 보지 못한다.
- 고객 전체 시설 이력이 아니라 해당 거래 연결 범위만 본다.

## 4. 본사 관리자

### MVP 권한과 책임

- 관리대장 기반 카테고리·동적필드·정책 등록/조회
- 카테고리 상태 `ACTIVE/PAUSED/REVIEW` 관리 및 감사
- Provider 승인/반려/정지/활성 관리
- 요청 후보와 배포 기록을 분리 조회
- 요청·견적·Transaction·완료·A/S·이력 연결 조회
- 분쟁 상태와 증빙 조회
- 시설·제품 연결 정정 승인과 감사

### 제한

- 원본 견적·완료증빙을 직접 수정하지 않는다.
- 민감정보 열람과 정정은 사유·권한·감사를 요구한다.
- MFA/재인증, 역할 세분화, 대량내보내기는 OI-035에서 후속 확정한다.

## 5. 시스템 행위자

- 요청 공개 시 필수 동적필드 검증
- 카테고리+시군구+승인+활성 후보 계산
- 후보와 별도 배포 기록 및 알림 이벤트/로그 생성
- 단일 견적 채택과 `Transaction` 원자 생성
- 고객 완료확정 후 `ServiceHistoryEntry` 멱등 생성
- A/S 상태변경 사건을 원 거래 이력에 추가
- 만료정책에 따른 요청·견적 종료

## 6. 데이터 가시성

| 데이터 | 고객 | Provider 채택 전 | 채택 Provider | 관리자 |
|---|---|---|---|---|
| 요청 공개정보 | 본인 전체 | 배포 요청의 마스킹 정보 | 거래 수행 범위 | 업무권한 범위 |
| 상세주소·연락처 | 본인 | 비공개 | 채택 후 최소범위 | 권한+사유+감사 |
| 견적 | 본인 요청의 전체 유효 견적 | 본인 견적만 | 본인 견적/채택조건 | 업무권한 범위 |
| Transaction·완료 | 본인 거래 | 접근 불가 | 본인 수행 거래 | 업무권한 범위 |
| 시설·제품 | 본인 소유 | 접근 불가 | 해당 거래 연결 범위 | 권한+감사 |
| 서비스/A·S 이력 | 본인 | 접근 불가 | 본인 수행 거래 범위 | 권한+감사 |
